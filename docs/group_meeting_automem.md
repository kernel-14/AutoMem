# AutoMem 组会分享：论文解读与 AppWorld 复现

> 论文：AutoMem: Text-Gradient Evolution of LLM-Agent Memory Architectures（华东师大 ICALK + 上海 AI Lab）
> 分享人：kernel14 | 复现仓库：github.com/kernel-14/AutoMem（appworld 分支）

---

## 1. 这篇论文在做什么

一句话：**把"给 LLM Agent 设计长期记忆"从手工设计问题变成搜索问题，用文本梯度驱动的进化循环来搜。**

背景：agent 记忆已经是标配（Mem0、Voyager、MemoryBank……），但每个系统都是人工设计好就固定了。这篇论文的第一个贡献是把这些系统拆开看——任何记忆系统都要回答四个问题：

| 模块 | 问题 | 典型选项 |
| --- | --- | --- |
| **Encode** | 记什么 | tip（技巧）/ insight（失败复盘）/ trajectory（轨迹摘要）/ workflow（流程模板）/ shortcut（可执行捷径） |
| **Store** | 怎么存 | json / vector / hybrid / graph / llm_graph |
| **Retrieve** | 怎么取 | hybrid / contrastive / cbr_rerank / graph / hyde / mmr |
| **Manage** | 怎么维护 | lightweight / json_full / tool_manager / graph_consolidate |

所有已知系统都是这个四维空间（31×5×6×4 = 3720 个组合，合法的 2573 个）里的一个固定点。论文 Table 1 把 15 个知名系统映射进去后发现：每个系统只精修一两个维度，其余停在默认值。

## 2. Motivation：三个预实验发现

作者先随机采样架构跑 benchmark，得到三个结论：

1. **强架构存在但任务特定**：随机采样的最好组合在 GAIA 上 69.7%，超过最强人造基线（MemoryBank 67.8%）；但换个 benchmark，最优组合四个维度全变
2. **模块强耦合**：好检索器配差编码器照样失败——不能单独调模块，必须整体搜索
3. **随机搜索浪费预算**：每次失败的评测只产生一个分数，分数只够淘汰、不够指导修改

由此推出核心问题：给定任务分布和评测预算，在 3720 个组合里找最优架构。难点：评测一个候选 = 让真实 agent 跑完整个任务，一个候选几百万 token。

**核心洞察**：失败轨迹里含有"往哪改"的结构化信息——该记的没记（extraction_gap）、记了没取到（retrieval_miss）、取到的是噪声（retrieval_noise）、内容过时（memory_stale）——每种失败模式直接映射到四个模块之一。把它结构化成"瓶颈-证据-行动"的文本，优化信号就从"分数"升级为"分数+方向"。

## 3. 方法

### 3.1 每轮循环

```
文本梯度 δt（上轮诊断）
   ↓
EGAS：proposer LLM 依据 (δt, 经验账本L, 观测图G, Pareto前沿Pt) 提出 3 个合法架构
   ↓
3 个候选并行跑固定任务批，产出准确率/增益/开销/轨迹
   ↓
Pareto 前沿更新（accuracy、memory lift、cost 三目标）
   ↓
FGMD：失败轨迹 → 范围过滤 → 模块归因 → 聚合 → 合成 δt+1
   ↓
账本 L / 观测图 G 更新（差分验证决定升降级）
```

### 3.2 EGAS：带外部记忆的 proposer

proposer 不只看最新反馈，挂三份跨轮状态：

- **经验账本 L**：principle 库，每条必须带证据链（轮次/候选/指标变化），置信度被验证 +0.10、被反驳 −0.30、每轮衰减 −0.05、低于 0.30 隐藏——防止 LLM 免检地积累信念
- **观测图 G**：按任务模式统计"模块选择 × 平均增益"——专门弥补编码失败的不可观测性（没记下来的东西在轨迹里是缺失，不是错误）
- **Pareto 前沿**：保三目标权衡，防止搜出"三倍 token 换一个点"的解

### 3.3 FGMD：失败 → 方向

三步流水：

1. **范围过滤**（纯规则）：剔除工具报错/超时/判分歧义——错误归因会污染搜索方向，宁可少要样本
2. **模块归因**（规则树 + LLM 兜底）：决策树问题序列就是记忆管线站序（池里有没有→取到没→注入没→过时没），失败模式映射到 E/S/R/M
3. **梯度合成**：整轮失败直方图 + 代表性轨迹 → δ = (瓶颈模块, 证据, 置信度, 建议编辑)

闭环关键在**差分验证**：上轮按诊断改了模块没变好→账本降级；变好了→升级。诊断给方向、EGAS 测试方向、validation 裁决方向。

### 3.4 两个保障设计

- **固定运行时（automem-runtime-v1）**：注入条数上限 3、每任务至多 1 次刷新、查询保留字面原文——全部代码写死，无开关。所有候选在相同执行策略下评测，**架构是唯一变量**（否则候选可以靠"多塞几条记忆"作弊，归因全部失效）
- **三段数据切分**：search 批（评候选）/ validation 批（冠军定期重评，防 search 批过拟合）/ test 批（held-out，记忆池里没有这些任务的痕迹，天然测迁移）

## 4. 论文实验结果

**三个 benchmark**（详见第 5 节）× 两个 backbone（Qwen3.5-122B-A10B / gpt-5.1-mini）：

| 指标 | 结果 |
| --- | --- |
| 主结果 | 6 个设置全部第一，平均 +2.8 点（GAIA 71.5% vs 最强基线 67.8%；token 128k vs 200k+） |
| vs 随机搜索 | 5 轮进化（143M token）超过 10 次随机采样（259M token）的最好成绩，**成本一半**；逐轮单调上升 55.8→71.5 |
| 消融 | 去 FGMD 掉到 64.2%，去 EGAS 掉到 57.9%——两组件缺一不可 |
| 定性 | 三个 benchmark 搜出三套完全不同的架构（GAIA→图存储+对比检索；WebWalkerQA→JSON+hybrid；xBench→CBM rerank），支撑"架构应随任务分布定制" |

Training-free：无梯度无微调，嵌入用冻结的 MiniLM。成本全在推理（一次完整搜索约 1.4 亿 token）。

## 5. Benchmark 介绍：各自是什么任务

**GAIA**（165 题，L1-L3）：通用助手型问答。问题很短但需要多步推理+工具，例如"第 15 届 RoboCup 哪个国家夺冠？"要拆成"搜主办城市→交叉验证年份→得国家"。部分题带附件（图/表/ZIP），答案永远是短事实。**特征：多步 web 推理 + 跨页实体关联。**

**WebWalkerQA**：纯网页导航 QA。每题给一个 root_url，答案藏在网站内部，agent 要沿站内链接走（walk）到证据页，如"给某统计局官网，问 2023 年 Q2 某指标是多少"。中英双语，按网站聚类切分（validation/test 来自未见过的网站）。**特征：导航→定位→取证，模式高度重复。**

**xBench-DeepSearch**（100 题）：中文深度搜索，需要多跳检索、跨信源交叉验证。**特征：长程探索 + 复用已解案例。**

**AppWorld**（我们复现用）：个人助理模拟环境。9 个日常 app（Spotify/Gmail/Venmo/Splitwise/Phone 等）、457 个 API、106 个虚拟人的数字生活。任务是自然语言指令（"把我上周听过的爵士乐整理成歌单发给某人"），agent 写 Python 调 API 完成，**用最终状态断言确定性判分**（无 judge LLM）。**特征：操作型任务、答案实例特定、用户习惯/流程可迁移。**

## 6. 我们的复现（AppWorld × 混元）

### 6.1 配置

- 任务模型 = proposer = 诊断 = 判分模型：混元 hy3（内部代理，OpenAI 兼容）
- AppWorld train+dev 共 147 任务：warmup 20 / search 50 / validation 37 / test 40
- 5 轮 × 3 候选，配对显著性检验 α=0.1，final runoff
- 全程约 17 小时、124M rollout tokens、682 个任务结果（与论文 GAIA 全量 143M 同量级）
- 另跑 5 个经典系统基线：按论文 Table 1 映射成固定架构点，统一运行时同待遇对比（学习 70 任务 + 测试 40 held-out）

### 6.2 结果

**进化搜索**：胜出架构 `r2_c2` = **tip+trajectory+workflow+insight 四类编码 / json / hybrid / lightweight**。

| 逐轮 best（fold 交替） | acc |
| --- | --- |
| R1 [tip] 单类型 | 12% |
| R2 四类编码 ← 最终冠军 | 28% |
| R3 四类（fold1: 12→16） | 16% |
| R4 五类+shortcut | 24% |
| R5 五类（fold1: 16→20） | 20% |
| runoff 全 50 任务 | r2_c2 16% 胜 r5_c1 14% |

**held-out 对比（40 任务）**：

| 系统 | 池规模 | held-out | vs 无记忆 |
| --- | --- | --- | --- |
| **AutoMem (r2_c2)** | 36 | **22.5%** | +2.5 |
| AWM（workflow/json） | 19 | **22.5%** | +2.5 |
| Voyager（shortcut/vector） | 11 | **22.5%** | +2.5 |
| Mem0（tip/vector） | 7 | 20.0% | 0 |
| MemoryBank（trajectory/vector） | 4 | 20.0% | 0 |
| 无记忆 | — | 20.0% | — |
| ExpeL（tip+insight/hybrid） | 54 | **15.0%** | **−5.0** |

### 6.3 复现结论（对照论文的主张）

| 主张 | 复现情况 |
| --- | --- |
| P1 失败可归因到模块并转化为方向 | **成立**——FGMD 产出真实梯度（R1 诊断"empty_retrieval_rate=0.56→扩编码"，R2 照做的候选夺冠）；账本 principle 抓到真信号 |
| P2/P3 定向搜索优于随机、逐轮积累 | 循环完整运转（propose→评测→归因→账本→champion 注入→配对检验→runoff）；随机对照组未跑 |
| P4 held-out 优势 | **弱证据**——+2.5 点 = 1 个任务，噪声范围内 |
| P5 架构随任务分布定制 | **成立且是独立证据**——AppWorld 搜出"广覆盖编码+朴素存储"，与论文三个 benchmark 的都不同 |

### 6.4 三个发现

1. **瓶颈在记忆利用端，不在检索端**：hit rate 0.44→0.88 翻倍，但准确率只动 1 个任务。82% 的任务败在长程 API 编排——hy3 的执行能力问题，记忆能补"不知道"，补不了"做不到"。论文用 Qwen3.5-122B 拿 +6.5，我们用 hy3 拿 +2.5，差异主要在任务模型把注入记忆用起来的能力
2. **过程性记忆才能迁移**：有增益的三个系统（AutoMem/AWM/Voyager）记忆里全是 workflow/shortcut 这类"怎么做"；纯语义记忆（tip/trajectory）零增益；ExpeL 的 54 条未管理失败 insight 净伤害 5 个点——**不管理的记忆比没有更糟**，这也是 AutoMem 给胜出架构配 lightweight 管理 + utility_audit 清理的原因
3. **AppWorld 的答案不可迁移，只有方法可迁移**：GAIA 的答案是事实（记了就能用），AppWorld 的答案是实例特定的（"我最喜欢的歌单里点赞最多的歌"取决于模拟用户数据）——能迁移的只有登录流程、API 套路，而这些大头已在系统提示里。这决定了该分布上"架构红利"的上限

### 6.5 工程副产品

- AppWorld 0.1.3 的 REPL 必须主线程跑（signal 超时）；线程失败会泄漏文件系统安全补丁
- AppWorld 会 patch `time.time/monotonic`（冻结世界时钟），计时需导入期函数引用
- 发现上游 bug：VectorStorage 的 canonical 导入静默丢弃无 embedding 单元（vector 的 metadata.json 不持久化 embedding）——潜伏在搜索引擎对纯 vector 候选的路径中（本次五轮冠军恰好都是 json/hybrid 未触发），值得给上游提 issue

## 7. 对我们工作的启发（讨论点）

1. **四维分解是通用语言**：任何记忆系统设计（包括我们的教师偏好记忆）都可以放进 E/S/R/M 框架定位——我们的差异化在哪一维？
2. **失败归因分类学可直接复用**：extraction_gap / retrieval_miss / injection_bad / memory_stale 的管线归因，适用于我们自己系统的错误分析
3. **固定运行时保证公平**：对比记忆策略时，注入条数/检索次数/查询改写必须冻结——这是实验设计的纪律
4. **"什么类型的记忆可迁移"取决于任务分布**：教育场景更像 AppWorld（操作型、实例特定）还是 GAIA（知识型）？决定了该记"偏好事实"还是"操作流程"
5. **局限**：好架构必须在菜单内（菜单本身是强先验）；元级推理依赖强 LLM；未测跨分布架构迁移

### 附：一分钟版本（如果只记得三句话）

1. 记忆设计是四维耦合问题，最优组合随任务分布变化，AutoMem 把它变成搜索问题
2. 核心机制是文本梯度：失败轨迹归因到模块，结构化成"瓶颈-证据-行动"，驱动带证据治理的进化循环——一半预算超过随机搜索
3. 我们在 AppWorld+混元上复现：机制全部成立，架构确实随分布定制（搜出的和论文三个 benchmark 都不同），但 lift 只有 +2.5 点且与 AWM/Voyager 并列——瓶颈定位在任务模型对注入记忆的利用能力，不在记忆架构本身
